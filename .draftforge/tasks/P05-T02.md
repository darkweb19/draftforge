# P05-T02 — Deterministic verification runner and secret scanning

Status: backlog

## Objective

Produce the machine half of review: execute the task contract's declared
verification commands inside the attempt worktree through an allowlisted,
shell-free boundary, and scan the attempt's diff and untracked candidate files
for secrets, recording locators without values. Both outputs are redacted
evidence that a reviewer model reads but cannot contradict.

## Acceptance criteria

- Verification commands are read from the contract's `## Verification` section.
  A contract with no such section, an empty one, or one whose commands are not
  allowlisted yields a `contract-violation` result rather than a silent pass.
- Only `npm run <script>` and `node <path>` with literal arguments execute. A
  command containing shell metacharacters, redirection, pipes, command
  substitution, an absolute or traversing path, or any other program is
  rejected before spawning. A test asserts nothing spawns for each rejection.
- Commands execute in the attempt worktree, never in the project root, with no
  shell, and inherit a minimal environment that carries no provider secrets.
- Each command records its literal command string, exit code, duration, and a
  redacted truncated transcript. A non-zero exit produces
  `verification-failure`; a timeout derived from `limits.taskTimeoutMinutes`
  produces `timeout` and reports whether the child was definitely terminated,
  matching the Phase 4 uncertain-termination contract.
- The secret scanner runs over the authoritative diff and over untracked
  candidate files in the worktree. It detects at minimum private key blocks,
  cloud provider access keys, bearer and authorization headers, `.env`-style
  assignments of credential-named variables, and high-entropy long tokens.
- A detection records only rule id, repository-relative path, and line number.
  A test asserts the matched value, any substring of it longer than a few
  characters, and any surrounding line content never appear in the returned
  findings or in any string the scanner produces.
- Both modules are pure application-layer functions over injected boundaries so
  they are unit-testable without a real repository or real subprocess, following
  the Phase 3 and Phase 4 injection precedent.
- `npm run check` passes.
