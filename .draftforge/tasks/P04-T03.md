# P04-T03 — Bounded worker prompt, workspace execution, and evidence

Status: done

## Objective

Execute one claimed task in its isolated workspace through the configured worker
route: build the least-context prompt, invoke a workspace-capable harness
without transparent side-effect retries, validate the worker result envelope,
verify the real Git diff against ownership, and persist redacted evidence before
moving the task to review or blocked.

## Acceptance criteria

- The worker prompt contains only the assigned task contract, repository agent
  rules, required context files, relevant ADRs, budget, workspace identity, and
  verification commands. Context paths are boundary-checked, symlinks that
  escape the worktree are rejected, and unrelated repository content is not
  included.
- `ModelRequest` and the harness process boundary carry an explicit worktree
  working directory. Harness capability data identifies workspace-capable
  execution; text-only API worker routes fail actionably before a task is
  claimed and never receive local filesystem access.
- A worker call that may mutate the worktree uses one provider attempt. Timeout
  or transient transport failure preserves the attempt/worktree and requires an
  explicit resume instead of the runner silently repeating the whole worker.
- The application layer strictly parses one result envelope with matching task
  and attempt IDs, status, summary, changed paths, commands run, evidence,
  risks, and suggested follow-ups. Unknown fields, malformed JSON, stale
  identities, or raw prose are rejected.
- Worker-reported changed paths are treated as claims. The authoritative Git
  diff from the workspace must be a subset of the owned paths; any unowned
  change or control-file change records evidence and blocks the task.
- Validated results and command evidence are redacted and atomically persisted.
  Raw model text, environment secret values, and provider credentials are never
  written to run artifacts.
- A successful worker result transitions `active -> review`; a blocked,
  malformed, timed-out, or scope-violating result follows the recorded Phase 4
  blocked path. The worker can never transition itself to `done`.
- Suggested follow-ups are recorded as evidence only and never expand the
  active contract.
- Deterministic tests inject the model runner and workspace, prove prompt
  minimization, capability rejection, one-call semantics, result parsing,
  redaction, real-diff scope enforcement, and correct state transitions.
- `npm run check` passes.

## Exclusions

- No API patch/tool execution protocol.
- No automatic reviewer, repair loop, merge, rollback, or task acceptance.
- No run-level concurrency or `run`/`resume` CLI.
- No token/cost accounting beyond preserving declared budgets and evidence.
