# P05-T05 — Review command, bounded repair loop, integration, and Phase 5 gate

Status: backlog

## Objective

Close Phase 5 by wiring the machine checks, the reviewer verdict, and usage
accounting into a `draftforge review` command; looping bounded repairs against
the same worktree; integrating accepted work onto the project branch with a
recorded rollback point; and proving with deterministic fixtures that injected
failures are rejected, recorded, repaired or blocked, and never silently marked
done.

## Acceptance criteria

- `draftforge review` reconciles attempts, then for each task in `review` runs
  the machine checks, calls the reviewer, and applies the effective outcome. No
  lock is held across a command execution, a scan, a model call, or a merge.
- Acceptance re-checks scope, re-runs the secret scan, records the project
  branch head as the rollback point, merges the attempt branch from a clean
  project root, records the integration commit, and only then transitions the
  task to `done`. A conflict or dirty project tree aborts the merge, retains the
  worktree, and blocks with `integration-conflict`.
- A repairable rejection transitions `review -> active`, increments the durable
  repair counter, and dispatches a repair attempt against the same worktree with
  the findings carried into the worker prompt. Reaching
  `limits.maxRepairAttempts` blocks the task with its classification and
  evidence intact.
- Terminal classifications never enter the repair loop. A secret detection, a
  scope violation, a contract violation, and an integration conflict each block
  on first occurrence.
- Every outcome is durable and idempotent: verdicts and machine results are
  persisted before the locked transition, and re-running `review` after a crash
  at any boundary neither re-calls the reviewer for a persisted verdict nor
  re-merges an already integrated attempt.
- A repair creates a new durable attempt reference while an explicit repair
  workspace adapter reuses the rejected attempt's retained worktree and branch.
  The new worker prompt carries only the persisted actionable findings; the
  ordinary Phase 4 worker prompt is unchanged when no repair context is present.
- A dependency fixture proves a successor becomes ready only after its
  predecessor is genuinely accepted and integrated, and that its worktree base
  commit contains the predecessor's work.
- Injected-failure fixtures cover a failing verification command, an
  out-of-scope diff, a planted synthetic secret, a malformed reviewer envelope,
  a reviewer rejection that repairs successfully, a rejection that exhausts the
  repair bound, and a merge conflict. Each asserts the task never reaches `done`
  and that recorded evidence contains no secret value.
- CLI help, exit codes, and summaries distinguish accepted, integrated,
  repairing, blocked, and no-work outcomes. `status` surfaces the repair counter,
  classification, rollback point, and run usage totals.
- README, `docs/PROTOCOL.md`, and `docs/ARCHITECTURE.md` document the review
  pipeline, the allowlisted verification shape, secret-scan behavior, the repair
  bound, integration requirements, rollback guidance, usage accounting, and the
  lock's new waiting behavior.
- The Phase 5 exit gate passes through the built CLI, `npm run check` passes,
  and canonical state plus `SESSION.md` are updated only after independent
  review accepts the implementation.

## Verification

- Run `npm run check`.
- Build the CLI and run `node dist/cli.js run`, `node dist/cli.js review`,
  `node dist/cli.js resume`, and `node dist/cli.js status` against the
  deterministic execution fixtures.

## Exclusions

- No automated rollback execution; the rollback point is recorded and documented,
  not applied.
- No release packaging, CI workflow, or cross-platform smoke matrix; those are
  Phase 6.
- No safe patch or tool protocol for API-backed workers; that remains a separate
  decision.
