## Acceptance criteria

- `draftforge run` reconciles state, claims up to available worker capacity, and
  executes selected non-conflicting tasks concurrently. Existing active
  attempts count toward the configured cap, and no lock is held during
  worktree or model operations.
- `draftforge resume` first reconciles attempt manifests, worktrees, result
  artifacts, events, and canonical task state. A persisted valid result is
  finalized to `review` without another model call; an interrupted attempt
  reuses the same identity and worktree; `review` and `done` tasks are never
  redispatched.
- Reconciliation is idempotent when run repeatedly and tolerates crashes after
  claim, worktree creation, first modification, result persistence, event
  append, state write, and session write. Event-ahead-of-state and orphan
  manifest cases resolve deterministically without inferring acceptance from an
  event alone.
- A deterministic parallel fixture proves two disjoint roots start before
  either finishes and never exceed `maxConcurrency`. A conflict fixture proves
  ancestor/descendant ownership serializes otherwise-ready tasks.
- A dependency fixture proves successors remain blocked while a predecessor is
  `active` or `review`. The test uses the trusted transition seam to simulate
  reviewer acceptance, then proves readiness recomputation dispatches the
  successor; runtime worker success never self-accepts.
- Failure fixtures cover malformed output, out-of-scope diffs, worker timeout,
  uncertain child termination, and interrupted worktrees. Each retains redacted
  evidence and prevents duplicate or unsafe dispatch.
- CLI help, exit codes, and summaries distinguish dispatched, resumed,
  deferred, review-ready, blocked, and no-work outcomes. `run` and `resume`
  refuse an unapproved plan or a non-workspace-capable worker route before
  changing task state.
- README and protocol documentation explain worktree retention, attempt
  evidence, capability limits, review handoff, and safe resume.
- The Phase 4 sample gate passes through the built CLI; `npm run check` passes;
  canonical state and `SESSION.md` are updated only after independent review
  accepts the implementation.
