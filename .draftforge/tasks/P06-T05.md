deterministic example on Windows, macOS, and Linux, then appears unchanged on
npmjs, GitHub Packages, and GitHub Release `v0.1.0` with publication metadata,

## Acceptance criteria

- One content-addressed `@draftforge-dev/draftforge@0.1.0` tarball is built from
  a clean release-candidate commit, inspected, retained as CI evidence, and
  used unchanged by every operating-system smoke job, both registry
  publications, and GitHub Release asset creation.
- On real Ubuntu, macOS, and Windows clean runners, the installed binary reports the expected version, scaffolds the deterministic example, passes `doctor`/`status` without exposing credentials, upgrades supported fixtures, and renders a matching handoff.
- The gate creates a deterministic interrupted execution without a live model call, installs the candidate over the project, resumes exactly once, reconciles persisted evidence without duplicate work, reaches the expected review boundary, and proves deterministic acceptance still integrates.
- The release check proves package name, version, tag, tarball metadata,
  documentation install command, changelog entry, Node engine, repository URL,
  public access, workflow artifact, and provenance settings agree; npmjs stays
  the canonical installation registry.
- Public `@draftforge-dev/draftforge@0.1.0` exists on npmjs with provenance,
  the same exact tarball and version exist as a public repository-linked GitHub
  npm package, and published GitHub Release `v0.1.0` contains that `.tgz` plus
  its checksum. Recorded digests for all three surfaces match the tested
  candidate.
- Publication is split into least-privilege jobs: npmjs receives only
  `id-token: write`, GitHub Packages receives only `packages: write`, and the
  GitHub Release receives only `contents: write`, in addition to the minimum
  read permissions each job needs. GitHub Packages uses `GITHUB_TOKEN` when
  supported; any cross-owner credential remains an explicit, separately
  approved prerequisite rather than an inferred workflow secret.
- Failure fixtures cover stale `dist/`, an inert binary, a missing template, version drift, future state, modified managed schema, tag mismatch, unscoped package name, and missing provenance; each fails before publication.
- The release run makes no live provider call and records no secret value; optional authenticated harness smoke stays separately opt-in and cannot be required for deterministic package acceptance.
- `npm run check` and platform-independent release checks pass locally, required
  GitHub jobs pass on Windows, macOS, and Linux, the user explicitly approves
  each publication boundary, and all three public `0.1.0` release surfaces are
  verified after publication.
- Canonical state and `SESSION.md` move to Phase 6 complete only after independent QA accepts the implementation and all three platform jobs are green.

## Verification

- Run `npm run check`.
- Run `node scripts/release-gate.mjs` against the content-addressed candidate tarball.
- Verify required Ubuntu, macOS, and Windows GitHub Actions jobs use and accept the same artifact digest.

## Exclusions

- No automatic rollback, self-update daemon, installer GUI, hosted control plane, telemetry, or analytics.
- No paid model or live provider credential in deterministic release acceptance.
- No state/session completion update before external matrix evidence and all
  three verified public publication records exist.
- No rebuilt, repacked, or registry-specific variant may substitute for the
  content-addressed tarball.
