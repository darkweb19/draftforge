# P06-T04 — Cross-platform CI, scoped publication, and npm provenance

Status: active

## Objective

Create the least-privilege automation that checks DraftForge and both constrained
npm artifacts on supported operating systems, then publishes tag-matched version
`0.1.0` as canonical `@draftforge-dev/draftforge` on npmjs and owner-scoped
`@darkweb19/draftforge` on GitHub Packages, then attaches the canonical artifact
to GitHub Release only after each identity and publication authority is verified.

## Acceptance criteria

- Pull requests and pushes run `npm ci`, `npm run check`, clean packing, tarball inspection, and installed-binary smoke on real Ubuntu, macOS, and Windows; the matrix includes Node.js 22 and any additional lane cannot replace the minimum-runtime lane.
- CI caches only npm download data, never `node_modules`, build output, tarballs, DraftForge run artifacts, local configuration, or environment files; jobs use minimal permissions and pinned current action versions.
- The release workflow triggers only from an intentional version tag, verifies the tag matches `package.json`, rebuilds from the tagged clean commit, runs the same checks, and publishes the exact tarball that passed smoke rather than rebuilding in the publish step.
- Before publication, metadata identifies public `@draftforge-dev/draftforge`
  version `0.1.0` with MIT license, repository, issues, Node.js runtime floor,
  and npmjs public access; release checks reject unscoped `draftforge`, any
  other package name or version, and a non-npmjs canonical install registry.
- The npmjs publication job publishes the already-tested tarball through npm
  trusted publishing/OIDC with provenance. Its elevated permission is limited
  to `id-token: write`; it stores no long-lived npm token and does not rebuild
  or repack the artifact.
- A separate GitHub Packages job stages `@darkweb19/draftforge@0.1.0` from the
  same tagged source commit. Only the packed manifest `name` and
  `publishConfig.registry` may differ from the canonical package. It publishes
  with the built-in repository `GITHUB_TOKEN`; its elevated permission is
  limited to `packages: write`. No new GitHub organization, PAT,
  `GH_PACKAGES_TOKEN`, or GitHub Packages bootstrap is a prerequisite.
- If first stable mirror publication creates a private GitHub package, the job
  records that partial external write and fails before npmjs publication. The
  owner changes visibility to Public, confirms repository linkage and Actions
  access, then reruns. The rerun verifies the existing version and digest rather
  than overwriting it; only then may npmjs and GitHub Release proceed.
- The canonical and mirror tarballs have different filenames and SHA-256
  digests because their embedded manifests have different names and registries.
  Checks record both digests, compare all packed content except the two allowed
  manifest fields, and install-test both tarballs on Ubuntu, macOS, and Windows.
  Both installed packages must expose the same `draftforge` binary and behavior.
- A separate GitHub Release job creates published release `v0.1.0` and attaches
  the same tested `.tgz` plus its checksum. Its elevated permission is limited
  to `contents: write`, and release checks prove the attached artifact digest
  matches the canonical npmjs tarball. The mirror digest is verified separately.
- npmjs remains the canonical public installation registry; GitHub Packages is
  a repository-linked mirror and must not change the documented default install
  command or the package's canonical registry metadata.
- Fork pull requests and ordinary pushes cannot publish; a tag/version mismatch,
  invalid identity, unexpected tarball, failed matrix job, missing npm trusted
  publisher, or digest mismatch fails before the affected publication changes
  external state. First-publish GitHub visibility can only be verified after the
  mirror write, so a private result stops all later external writes as specified
  above.
- Workflow tests parse YAML and package metadata to guard triggers, separated
  least-privilege job permissions, matrix coverage, artifact identity,
  registry destinations, the constrained mirror transformation, both OS-matrix
  artifacts and digests, GitHub Release assets, provenance, and secret absence;
  routine local tests do not call GitHub or either npm registry.
- `npm run check` passes.

## Verification

- Run `npm run check` and `node scripts/release-check.mjs` against a locally packed tarball.
- On GitHub, require green Ubuntu, macOS, and Windows installed-artifact jobs
  before testing the tag-gated publication path, and verify the final public
  `0.1.0` records, the allowed cross-registry manifest delta, each registry's
  recorded digest, and the canonical digest agreement between npmjs and GitHub
  Release `v0.1.0`.

## Exclusions

- No publication under the unscoped `draftforge` name.
- No classic npm automation token, password, OTP, or secret value in files, logs, fixtures, workflow inputs, or task evidence.
- No stable npmjs publish until control of `@draftforge-dev` and the npm trusted
  publisher configuration are confirmed; its one-time bootstrap remains an
  explicit manual prerequisite.
- No product-source or package-content mutation between registry artifacts;
  only the approved mirror manifest name and registry deltas are allowed.
- No new GitHub organization, PAT, `GH_PACKAGES_TOKEN`, or GitHub Packages
  bootstrap. The built-in `GITHUB_TOKEN` is the only mirror publication token.
