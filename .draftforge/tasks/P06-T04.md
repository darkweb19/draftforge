# P06-T04 — Cross-platform CI, scoped publication, and npm provenance

Status: active

## Objective

Create the least-privilege automation that checks DraftForge and its exact npm
artifact on supported operating systems, then publishes tag-matched version
`0.1.0` to npmjs, GitHub Packages, and GitHub Releases only after each registry
identity and publication authority is explicitly verified.

## Acceptance criteria

- Pull requests and pushes run `npm ci`, `npm run check`, clean packing, tarball inspection, and installed-binary smoke on real Ubuntu, macOS, and Windows; the matrix includes Node.js 22 and any additional lane cannot replace the minimum-runtime lane.
- CI caches only npm download data, never `node_modules`, build output, tarballs, DraftForge run artifacts, local configuration, or environment files; jobs use minimal permissions and pinned current action versions.
- The release workflow triggers only from an intentional version tag, verifies the tag matches `package.json`, rebuilds from the tagged clean commit, runs the same checks, and publishes the exact tarball that passed smoke rather than rebuilding in the publish step.
- Before publication, metadata identifies public `@draftforge-dev/draftforge`
  version `0.1.0` with MIT license, repository, issues, Node.js runtime floor,
  and npmjs public access; release checks reject unscoped `draftforge`, any
  other package name or version, and a non-npmjs canonical install registry.
- The npmjs publication job publishes the already-tested tarball through npm
  trusted publishing/OIDC with provenance. Its elevated permission is limited
  to `id-token: write`; it stores no long-lived npm token and does not rebuild
  or repack the artifact.
- A separate GitHub Packages job publishes that same tarball and version as a
  public, repository-linked GitHub npm package. Its elevated permission is
  limited to `packages: write`. It uses the repository `GITHUB_TOKEN` where the
  selected GitHub namespace and package linkage support it; if the npm scope's
  owner differs from the GitHub repository owner and `GITHUB_TOKEN` cannot
  publish or link the package, publication requires a separately approved,
  least-privilege GitHub credential. The workflow must not guess, silently add,
  or broaden that credential.
- A separate GitHub Release job creates published release `v0.1.0` and attaches
  the same tested `.tgz` plus its checksum. Its elevated permission is limited
  to `contents: write`, and release checks prove the attached artifact digest
  matches the tarball published to both registries.
- npmjs remains the canonical public installation registry; GitHub Packages is
  a repository-linked mirror and must not change the documented default install
  command or the package's canonical registry metadata.
- Fork pull requests and ordinary pushes cannot publish; a tag/version mismatch,
  private identity, unexpected tarball, failed matrix job, missing npm trusted
  publisher, unresolved GitHub Packages authority, or digest mismatch fails
  before any publication job changes external state.
- Workflow tests parse YAML and package metadata to guard triggers, separated
  least-privilege job permissions, matrix coverage, artifact identity,
  registry destinations, GitHub Release assets, provenance, and secret absence;
  routine local tests do not call GitHub or either npm registry.
- `npm run check` passes.

## Verification

- Run `npm run check` and `node scripts/release-check.mjs` against a locally packed tarball.
- On GitHub, require green Ubuntu, macOS, and Windows installed-artifact jobs
  before testing the tag-gated publication path, and verify the final public
  `0.1.0` records and digest agreement across npmjs, GitHub Packages, and GitHub
  Release `v0.1.0`.

## Exclusions

- No publication under the unscoped `draftforge` name.
- No classic npm automation token, password, OTP, or secret value in files, logs, fixtures, workflow inputs, or task evidence.
- No public publish until control of `@draftforge-dev`, the npm trusted
  publisher configuration, and GitHub Packages publication authority are all
  confirmed.
- No fallback that rebuilds, repacks, or mutates the tested tarball separately
  for npmjs, GitHub Packages, or the GitHub Release.
- No unapproved cross-owner GitHub credential or broader repository/package
  permission to make GitHub Packages publication succeed.
